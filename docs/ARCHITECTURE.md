# Cozy Food Factory implementation map

This document describes the current Unity **6000.5.2f1** prototype. The [Cozy Food Factory GDD](COZY_FOOD_FACTORY_GDD.md) describes intended rules; this map records what the repository currently does. Phase 1 provides a food delivery loop alongside the still active Fantasy Rune Factory prototype.

## Phase 1 food loop

| Layer | Implementation | Current behavior |
| --- | --- | --- |
| Food identity | [`FoodItemData.cs`](../Assets/_Project/Scripts/Food/FoodItemData.cs), [`CropDefinition.cs`](../Assets/_Project/Scripts/Food/CropDefinition.cs) | A food item has an ID, a `RawIngredient` or `ProcessedFood` kind, and a positive sell value. Equality and hash codes use ID and kind, keeping delivery counts independent of price. Crop definitions validate a raw output and a growth duration. |
| Farm Plot | [`FarmPlotProcess.cs`](../Assets/_Project/Scripts/Food/FarmPlotProcess.cs), [`FarmPlot.cs`](../Assets/_Project/Scripts/Food/FarmPlot.cs) | The player selects a crop; the process accumulates mature crops up to capacity and pauses while full. Changing or clearing the crop resets growth and mature crops. The plot does not output to belts. The prefab offers Apple and Tomato initially; Onion requires the first Market order unlock, and Basil requires a Seed Shop purchase. |
| Harvester | [`HarvesterPlacementBehavior.cs`](../Assets/_Project/Scripts/Food/HarvesterPlacementBehavior.cs), [`HarvesterProcess.cs`](../Assets/_Project/Scripts/Food/HarvesterProcess.cs), [`Harvester.cs`](../Assets/_Project/Scripts/Food/Harvester.cs) | A rotatable 1×2 Harvester covers one Farm Plot and one free cell. It collects from the covered plot on a timer, buffers `FoodItemData`, and exposes an output cell beyond its free cell to the belt system. A full buffer pauses collection. |
| Belts | [`BeltTransportSystem.cs`](../Assets/_Project/Scripts/Logistics/BeltTransportSystem.cs), [`BeltTransportCoordinator.cs`](../Assets/_Project/Scripts/Logistics/BeltTransportCoordinator.cs) | `ITransportItem` is the shared payload contract. The system transfers items among belts, `IItemOutputSource` implementations, and `IItemInputReceiver` implementations. It checks receiver acceptance before consuming a belt item and advances once per `LateUpdate`. |
| Market | [`MarketReceiver.cs`](../Assets/_Project/Scripts/Food/MarketReceiver.cs), [`MarketInventory.cs`](../Assets/_Project/Scripts/Food/MarketInventory.cs), [`Market.cs`](../Assets/_Project/Scripts/Food/Market.cs), [`MarketPanel.cs`](../Assets/_Project/Scripts/Food/MarketPanel.cs) | The fixed scene Market accepts valid raw and processed food from any belt direction. It counts cumulative deliveries by ID and kind, awards each item's sell value as regular currency, and displays the balance, order progress, and Seed Shop in a scrollable panel. |

[`Prototype.unity`](../Assets/_Project/Scenes/Prototype.unity) wires the Farm Plot and Harvester prefabs to placement keys **5** and **6**, the transport coordinator, a fixed Market at grid cell **(10, 4)**, and a legacy Hub at **(10, 1)**. [`BuildingPlacementController.cs`](../Assets/_Project/Scripts/Buildings/BuildingPlacementController.cs) reserves the Market and Hub cells in [`GridOccupancy.cs`](../Assets/_Project/Scripts/Buildings/GridOccupancy.cs). Its Harvester placement path permits an overlay only when the Farm Plot is present and the Harvester's other cell is free. The covered plot remains alive and configurable through [`ObjectivePanel.cs`](../Assets/_Project/Scripts/UI/ObjectivePanel.cs); removing the Harvester reveals it again. Harvester group copying and cut/move are unavailable because those paths do not carry the underlying plot and the Harvester has no move-state implementation.

The scene still permits Farm Plot placement on any unoccupied cell. The GDD's designated farmable land rule has no map data or placement check yet. The prototype defaults for growth, collection interval, and buffer sizes are serialized in the prefabs, not finalized balance.

The current sample values are **2 seconds** to grow one crop, **4** mature crops per plot, **1 second** between Harvester collections, **4** Harvester output slots, **1 second** for Processor completion, **4** units of capacity per sample property source, and **1** regular currency per sample food delivery. The first order asks for **3 apples** and directly unlocks Onion. These are scene and prefab prototype settings, not finalized GDD balance or a general progression rule.

## Phase 2 property supply prototype

[`CookingPropertyNetwork.cs`](../Assets/_Project/Scripts/Food/CookingPropertyNetwork.cs) models Heat, Moisture, Time, and Air separately from belt items. Each grid connection belongs to one environmental source; collectors must touch that source, pipes extend through cardinal neighbors, and a connection cannot join two sources. The source's Inspector capacity is compared with connected demand. An overloaded network reports unavailable supply for all test endpoints because consumer allocation during shortages is still undecided. Removing a link recalculates live connectivity; disconnected sections retain their source owner.

[`PropertySupplyPlayMode.cs`](../Assets/_Project/Scripts/Food/PropertySupplyPlayMode.cs) provides temporary Play Mode controls on the right side of the screen. Select a source and the Collector tool, then click an adjacent cell. Pipe extends the network; Test load places a one-unit endpoint; Remove deletes placed connections. Green endpoints have available supply; red endpoints are disconnected or over capacity. The scene contains one sample node per property, each with a provisional capacity of four. All source and connection cells use `GridOccupancy`, so buildings and belts cannot be placed on them. Processor property demand attaches only to its rotated property-facing outside cell, counts against source capacity, and frees capacity on removal. Construction costs and final pipe controls remain open.

## Phase 2 Processor loop

The scene's key **7** option uses the finalized three-cell Processor footprint: chamber (0, 1), property module (1, 1), and lower support (0, 0); (1, 0) remains open. [`ProcessorPortLayout.cs`](../Assets/_Project/Scripts/Food/ProcessorPortLayout.cs) rotates the cells and three ports together. A belt enters from the chamber's West side in the default orientation, a pipe connects at the property module's South side through the open corner, and a finished-food belt begins beyond the chamber's North side. The controller installs [`ProcessorPlacementBehavior.cs`](../Assets/_Project/Scripts/Food/ProcessorPlacementBehavior.cs) for that scene option at runtime; the behavior initializes [`Processor.cs`](../Assets/_Project/Scripts/Food/Processor.cs) and registers food input/output with the existing belt coordinator.

[`ProcessingRecipe.cs`](../Assets/_Project/Scripts/Food/ProcessingRecipe.cs) matches food identity and one supplied property. [`ProcessorProcess.cs`](../Assets/_Project/Scripts/Food/ProcessorProcess.cs) accepts food only for exactly one matching recipe, pauses if the active property supply is lost, and holds finished output until a belt can take it. The scene has one provisional recipe, Apple + Air → Dried Apple, and a provisional one-second processing duration. Clicking a Processor opens state, supply, and recipe feedback; a red marker indicates product output waiting. Compost and final balance are not part of this loop.

## Phase 2 Basic Mixer loop

[`BasicMixerPortLayout.cs`](../Assets/_Project/Scripts/Food/BasicMixerPortLayout.cs) defines the finalized 2×2 footprint: input A at (0,0) from West, input B at (0,1) from West, and output at (1,1) toward East, with all ports rotating with placement. [`BasicMixer.cs`](../Assets/_Project/Scripts/Food/BasicMixer.cs) registers two separate food receivers and one output source with the existing belt coordinator. The two receivers share a per-step reservation, so simultaneous belt arrivals are accepted one at a time and the second can be checked against the first ingredient. [`MixingRecipe.cs`](../Assets/_Project/Scripts/Food/MixingRecipe.cs) matches unordered food pairs; [`BasicMixerProcess.cs`](../Assets/_Project/Scripts/Food/BasicMixerProcess.cs) accepts a second ingredient only for one unique recipe and holds its output until a belt is available. The scene's key **8** option has the GDD's provisional Tomato + Onion → Vegetable Base recipe; the Farm Plot prefab offers Tomato and Onion for this loop. The Mixer has no property-network input.

## Phase 3 recipe discovery tracking

[`RecipeDiscoveryRegistry.cs`](../Assets/_Project/Scripts/Food/RecipeDiscoveryRegistry.cs) records the first completed production of each processing or mixing recipe. The Processor records when its timer completes; the Mixer records when its second ingredient creates output. The placement controller shares one registry across both machine types and exposes its read-only discovered recipe list and first-discovery event. [`RecipeDiscoveryPanel.cs`](../Assets/_Project/Scripts/UI/RecipeDiscoveryPanel.cs) uses that event for a dismissible first-discovery popup and reads the live list for a minimal Recipe Book. The recipe's output food ID serves as its display name. Discoveries are held for the current scene session; saved progression and the GDD's full discovery animation are not implemented.

## Phase 3 orders and shared unlocks

[`FoodOrder.cs`](../Assets/_Project/Scripts/Food/FoodOrder.cs) defines serializable order requirements and generic unlock keys identified by category and ID. `FoodOrderSequence` activates authored orders in array order, one at a time. Each order snapshots Market delivery counts when activated, so earlier sales do not fill later orders; after completion it records the order once, grants its unlock keys to a shared `UnlockState`, and activates the next order. The Market exposes the authored orders, completed orders, active progress, and unlock state to the UI and future systems.

The scene currently authors only the existing provisional order: deliver three apples to grant the `crop` / `Onion` key and make Basil seeds available in the shop. [`FarmPlot.cs`](../Assets/_Project/Scripts/Food/FarmPlot.cs) reads the shared unlock state when selecting crops, including on plots placed before an unlock. The Market panel displays active and completed orders and their unlocks without naming specific foods. Additional orders can be authored, but their content, rewards, and final activation policy remain undecided; array order is the prototype continuation of the former single active order. The direct Onion grant preserves prototype behavior. Order and unlock state last only for the current scene session.

## Basic Seed Shop

[`Market.cs`](../Assets/_Project/Scripts/Food/Market.cs) holds serialized seed offers and a `SeedShop` that reads the existing Market currency and shared `UnlockState`. An offer can require an unlock key before it is available. Its state is locked, available but unaffordable, affordable, purchased, or already unlocked through another source. A successful purchase spends currency once and grants a `crop` unlock; a failed or repeat purchase spends nothing. The Market panel displays these states and purchase buttons.

The sole scene offer is provisional **Basil Seeds** for **3 regular currency**, made available by the existing Apple order. The Farm Plot prefab includes Basil as a locked crop. The GDD intends region restoration before shop availability; that step is absent, so the order grants shop availability directly for this prototype. The Basil crop, price, growth duration, and reward are sample content, not final balance or progression design. Seed purchases unlock crop selection rather than consuming currency for each planting. Seed Shop state is not persisted.

## UI input boundary

The Market panel scrolls within the lower left half of the screen. Its pointer area blocks world placement and camera wheel zoom. The Recipe Book and discovery popup block world placement, and the Recipe Book blocks camera wheel zoom while hovered. The legacy objective and machine configuration panels block world placement when hovered, including clicks on crop selection buttons. The property supply debug panel separately handles its own clicks. These IMGUI panels still use fixed screen positions, so the Recipe Book and property debug panel can overlap on small windows; responsive layout is not implemented.

These dependencies are compatibility obligations of the current scene, not evidence that runes are part of Cozy Food Factory's intended design. Removing them requires a separate migration and scene validation.

## Tests and next implementation boundary

[`Tests/EditMode/`](../Assets/_Project/Tests/EditMode/) contains focused tests for Farm Plot growth, Harvester buffering and overlay placement, generic food transport, Market identity counts and currency spending, order progress and crop unlocking, Seed Shop availability and purchases, the plot-to-Market process chain, property network connectivity/capacity/isolation, Processor port rotation, Mixer port rotation and input ownership, recipe matching, discovery deduplication and popup queue behavior, and held output. These are Unity EditMode tests; compilation alone does not establish that they ran. The scene's full Play Mode loop requires manual verification in the running Editor.

Before extending food machines, account for these observed boundaries:

- `FoodItemData` stores ID and kind. Processing recipes match this identity with one property; there is no multi-property runtime model.
- [`BeltTransportSystem.cs`](../Assets/_Project/Scripts/Logistics/BeltTransportSystem.cs) maps one receiver to each input cell and reserves transfers per step. The Basic Mixer uses two cell receivers with a shared per-step reservation, so only one ingredient enters it per transport step. Invalid or ambiguous second ingredients remain on their belts.
- Legacy Engraver and Element Infuser recipes operate on `RuneData` and require manual configuration. They are not an implementation of the GDD's automatic food recipe matching.
- Food belts and property supply use separate models. The Processor uses the finalized first port layout. Property shortage allocation and intersection rules remain undecided; over-capacity supply currently reports unavailable to connected demands.
- Belt carrier and debug names still reflect rune origins. Food uses the same placeholder belt item visual, so distinct food identities are visible through debug text and Market counts rather than item art.
- Order progress and cumulative unlocks are held only in scene memory. The sequence supports multiple authored orders, but scene content still has one. Persistence and the transition from the prototype's direct shop availability to region restoration need separate design and implementation.
- Currency now buys the provisional Basil seed unlock; food construction, upgrades, and land purchases do not consume it. Farm Plots can still be placed outside designated farmable land.
